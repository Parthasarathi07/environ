Four specifications, one conclusion

Returns are monthly, in percent. Every model includes year fixed effects and standard errors clustered by firm — the same firm appears ~95 times, so ordinary errors would make everything look significant.

Do high-ESG firms look different as businesses?

Firm-level averages over the whole sample — one point per firm, so no clustering issue. If the operating differences are near zero but the market differences are not, the story is about investor beliefs, not about cash flows.

    What this project is not

    It is not a claim about the real world. It is a working analysis pipeline whose conclusions are produced by the data you give it. The demo panel is synthetic and labelled as such in every view. The moment you load MSCI or ESG-Book scores with real prices, the verdict text above regenerates — it is computed, never hard-coded.

    Try it: break the result on purpose

    Every conclusion here follows from three assumed coefficients. Re-run the generator with them zeroed and the dashboard flips to "nothing to see":

    python -m environ.data.generate_data \
  --level-bp 0 --momentum-bp 0 --level-vol-pct 0

    This is the test I would apply to any ESG study in a pitch. Almost nobody publishes it.

    Column contract

    Upload a CSV with these columns — one row per firm per month — and every number on this page, including the verdict sentences, is recomputed. No code changes.

    Getting real data, free
    1. Ratings: ESG-Book publishes quarterly ESG scores for 4,000+ firms with a permissive licence. Export the quarterly panel to CSV.
    2. Prices: pip install yfinance, then download monthly adjusted closes for the tickers in your ratings file, 2016-01 to the present.
    3. Sectors: take GICS from the ratings file, or map tickers to a sector using the S&P classification published by each index provider.
    4. Build: python -m environ.data.build_real_panel --ratings … --prices … computes z-scores, the 12-month momentum column and the neutralisation inputs for you.

    If a step is unavailable, the analysis runs on whatever subset you have — the loader reports which columns it derived and which it had to skip.
